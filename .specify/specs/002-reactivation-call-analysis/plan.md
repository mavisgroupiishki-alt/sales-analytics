# Технический план: Полный анализ звонков реанимации

**Спека:** [spec.md](spec.md)
**Создан:** 2026-10-02

## Архитектура

```text
Фоновый worker реанимации
  ├─ Bitrix: все завершённые звонки по ID сделки реанимации
  ├─ аудио → расшифровка → самостоятельный immutable-анализ Jarvis
  ├─ private Postgres: записи, связи и результаты
  └─ очередь: <= 8 последних summaries + комментарии + поля → рекомендация
```

## Решения

- В выборку попадают только звонки, в Bitrix напрямую связанные со сделкой: не предполагаем связь через компанию или контакт.
- Сканер очереди остаётся быстрым и read-only: анализ запускается отдельной фоновой задачей, а не в HTTP-ответе дашборда.
- Повторные запуски идемпотентны: существующий анализ не запускается заново.
- Неизменяемые анализы и CRM-связи сохраняются в private Jarvis Postgres; в браузер передаётся только краткое доказательство.

## Риски

- Старые записи могут быть удалены из Bitrix или быть нулевой длины: это показывается как «без записи», а не маскируется.
- Первый прогон может быть долгим: он должен выполняться в фоне и не блокировать дашборд.
- Ограничение контекста в восемь summaries обязательно сохраняется, хотя анализируются все записи.
